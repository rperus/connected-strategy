## 🔍 Detalle Profundo de Hallazgos Críticos

### 🔴 P0-1: Corrupción del Score de Salud del Proyecto (Unexpected Nulls)
* **Ubicación:** `apps/server/src/db/repositories/projects.ts` (L67) & `apps/server/src/services/churnPredictor.ts`
* **Mecánica del Fallo:**
  1. Cuando el scanner registra un nuevo proyecto o la UI actualiza un proyecto, el parámetro opcional `health_score` no se pasa en el objeto, por lo que el repositorio ejecuta:
     ```typescript
     project.health_score ?? null
     ```
     Esto sobreescribe explícitamente a `NULL` el valor `100` por defecto configurado en la base de datos.
  2. Al ejecutarse el planificador de fondo, la función `checkChurnRisks()` lee este registro: `p.health_score` is `null`.
  3. Si la última ejecución fue reciente (hoy), se cae en la lógica de recuperación:
     ```typescript
     newHealthScore = Math.min(100, p.health_score + 5)
     ```
     En Javascript, `null + 5` se evalúa como `5`. 
  4. Dado que `5 !== null`, se dispara una query que actualiza el proyecto con un **5% de salud** y genera un log de telemetría de decremento masivo.
* **Solución Propuesta:** Cambiar el fallback en el repositorio a `project.health_score ?? 100` y usar `COALESCE` en la query SQL del `upsertProject` para no pisar el valor previo si existe.

### 🔴 P0-2: Ausencia Total de Integridad Referencial Física (Orphan Rows)
* **Ubicación:** `apps/server/src/db/index.ts` (Fase de inicialización)
* **Mecánica del Fallo:**
  Aunque se ejecuta `db.pragma('foreign_keys = ON')`, las sentencias `CREATE TABLE` de `worksheet_answers`, `analysis_jobs`, `v3_runs` y `project_telemetry_logs` no definen cláusulas de clave foránea (`FOREIGN KEY (project_id) REFERENCES projects(id)`).
  Cuando se llama a `DELETE FROM projects WHERE id = ?`, el motor de base de datos borra el registro de la tabla padre pero deja intactas todas las respuestas, ejecuciones e historiales en las tablas secundarias como basura huérfana en el disco.
* **Solución Propuesta:** Redefinir la migración inicial de las tablas en `db/index.ts` para incluir claves foráneas explícitas con cláusula `ON DELETE CASCADE`.

### 🟡 P1-1: Concurrencia Vulnerable a Excepciones Directas (No `busy_timeout`)
* **Ubicación:** `apps/server/src/db/index.ts` & `packages/agents/src/v3/db/index.ts`
* **Mecánica del Fallo:**
  SQLite restringe la escritura a un único proceso. En un entorno activo donde el backend Express expone APIs de guardado rápido, mientras la cola de ejecución síncrona `better-sqlite3` realiza pipelines pesados o telemetría, la ausencia de un `busy_timeout` provoca que cualquier intento de escritura concurrente falle inmediatamente lanzando un error fatal de `SQLITE_BUSY: database is locked`.
* **Solución Propuesta:** Añadir `db.pragma('busy_timeout = 5000')` inmediatamente tras la inicialización del motor en ambos archivos de conexión.

### 🟡 P1-2: Operaciones N+1 en loops (Fase de Scheduler)
* **Ubicación:** `apps/server/src/services/churnPredictor.ts` (L27-28)
* **Mecánica del Fallo:**
  La iteración sobre los proyectos vulnerables a churn ejecuta:
  ```typescript
  db.prepare(`UPDATE projects SET health_score = ? WHERE id = ?`).run(newHealthScore, p.id);
  ```
  Esto compila (prepara) y ejecuta la sentencia de forma repetitiva en cada iteración del bucle, asfixiando al motor SQLite de forma innecesaria.
* **Solución Propuesta:** Preparar la sentencia *una sola vez* al inicio de la función (`const stmt = db.prepare(...)`) y ejecutar únicamente el método `run()` en el bucle.

## 🛠️ Plan de Mitigación y Código Seguro (Safe-Fix Plan)

### 1. Corrección del Repositorio de Proyectos (`apps/server/src/db/repositories/projects.ts`):
Reemplazar la llamada en `upsertProject` (L67) para asegurar que un `health_score` no calculado mantenga un valor saludable o respete el estado previo:
```typescript
// En L67:
project.health_score !== undefined ? project.health_score : (getProject(project.id)?.health_score ?? 100)
```

Y en la sentencia SQL de `upsertProject` (L49-58) usar `COALESCE`:
```sql
ON CONFLICT(id) DO UPDATE SET
  name = excluded.name,
  path = excluded.path,
  stack = excluded.stack,
  maturity = excluded.maturity,
  tags = excluded.tags,
  last_scanned = excluded.last_scanned,
  health_score = COALESCE(excluded.health_score, projects.health_score, 100),
  last_execution_date = COALESCE(excluded.last_execution_date, projects.last_execution_date),
  updated_at = excluded.updated_at
```

### 2. Configuración de `busy_timeout` en Inicializaciones:
Añadir la configuración en `apps/server/src/db/index.ts` (L26) y `packages/agents/src/v3/db/index.ts` (L16):
```typescript
db.pragma('busy_timeout = 5000');
```

### 3. Optimización del Loop en Churn Predictor (`apps/server/src/services/churnPredictor.ts`):
Optimizar la preparación de consultas fuera del loop:
```typescript
export function checkChurnRisks() {
  const db = getDb();
  const now = new Date();

  const projects = db.prepare(`SELECT id, health_score, last_execution_date FROM projects`).all() as any[];

  const updateStmt = db.prepare(`UPDATE projects SET health_score = ? WHERE id = ?`);
  const telemetryStmt = db.prepare(`INSERT INTO project_telemetry_logs (project_id, event_type) VALUES (?, ?)`);

  for (const p of projects) {
    if (!p.last_execution_date) continue;
    // ... cálculo ...
    if (newHealthScore !== p.health_score) {
      updateStmt.run(newHealthScore, p.id);
      telemetryStmt.run(p.id, 'HEALTH_SCORE_UPDATED');
    }
  }
}
```
